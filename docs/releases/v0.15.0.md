# Publicar v0.15.0 (2026-11-15)

Guía para quien despliega (una persona o un agente). Más contexto del proceso: [docs/RELEASE.md](../RELEASE.md).

## El comando

Con el PR de la versión **mergeado en `master`** y su CI en verde, desde la carpeta del proyecto:

```bash
npm run release:deploy
```

Es el mismo en PowerShell, Bash y CI. No hay que pasarle versión ni commit: se pone en `master`, lo actualiza (si no tienes cambios sin guardar), lee la versión que declara (`0.15.0`), encuentra su commit (el merge del PR de la versión) y:

1. Comprueba que ese commit lleva la versión en `package.json` y su sección fechada del CHANGELOG.
2. Crea y sube el tag anotado `v0.15.0` (si ya existe, comprueba que apunta a ese commit; un tag publicado no se mueve).
3. Crea la release de GitHub con las notas del CHANGELOG (si ya existe, la deja).
4. Deja la rama `release` (la de producción en Vercel) en ese commit, solo si es fast-forward. Si no lo es, **no fuerza nada** y se detiene con un aviso.

Se puede repetir sin miedo: lo que ya está hecho se salta. Antes de lanzarlo de verdad se puede ver qué haría:

```bash
npm run release:deploy -- --dry-run
```

Otras opciones: `--no-prod` (tag y release de GitHub sin tocar `release`), `0.15.0` como argumento (una versión concreta, por si `master` ya declara otra) y `--sha COMMIT` / `--remote NOMBRE` (casos raros).

Necesita `git` con permiso de push de tags y de la rama `release`, y `gh` (GitHub CLI) con sesión iniciada. Los agentes de IA que preparan la versión **no** pueden empujar tags ni `release`: lo lanza una persona o el agente de despliegue con esos permisos.

## Lo único que queda a mano: Vercel

Cuando el script termina, la rama `release` ya está bien puesta. Falta desplegarla en Vercel:

- Vercel → proyecto `pug-ide` → **Deployments** → el despliegue de la rama `release` (su commit es el de la versión) → **Promote to Production** (o **Redeploy**). Si la rama de producción configurada es `release`, el push ya lo habrá lanzado: comprueba que su despliegue está en verde.

## Los instaladores de escritorio salen solos

Al publicarse la release, el flujo `Escritorio` (`.github/workflows/desktop.yml`) construye los instaladores de Windows, macOS y Linux (sin firmar), los prueba y los **adjunta a la release** de GitHub, con el aviso de «sin firmar» en sus notas. Tarda unos 15–25 minutos y no hay que hacer nada:

- Mira en GitHub → **Actions** → **Escritorio** que la web y las tres máquinas (Linux, Windows, macOS) terminan en verde, y que la release de `v0.15.0` tiene sus archivos (`.exe`, `.dmg`, `.AppImage`, `.deb`, `.rpm`).
- Si algo falla, repítelo: Actions → **Escritorio** → *Run workflow* con el tag `v0.15.0` (o `gh workflow run desktop.yml -f tag=v0.15.0`).
- Guía para quien instala: [docs/INSTALAR.md](../INSTALAR.md).

## Comprobación a mano en producción

Con una ventana de incógnito (el service worker de la PWA cachea la versión anterior):

- Carga el editor y la vista previa, y el Workspace muestra `v0.15.0`.
- `Ctrl+V` pega en el editor.
- La consola del navegador no muestra violaciones de CSP.
- Una plantilla con imágenes remotas se ve.

## Si algo falla

- **«No es fast-forward»:** `release` tiene algo que `master` no tiene. No fuerces nada: investígalo y avisa.
- **El tag ya existe y apunta a otro commit:** un tag publicado no se mueve. Investígalo.
- **`gh` falla:** inicia sesión con `gh auth login` y repite el comando (el tag no se vuelve a crear).
- **Volver atrás, rápido:** en Vercel → Deployments, el despliegue de producción anterior → **Promote to Production** (o **Instant Rollback**).
- **Volver atrás, definitivo:** corregir en `master` con un PR, publicar un parche y repetir. No se reescribe el historial ni se reutilizan tags.

## Los mismos pasos a mano (por si el script no se puede usar)

```bash
git fetch origin master release --tags
```

```bash
git tag -a v0.15.0 <SHA del merge del PR de la versión> -m "PugIDE 0.15.0"
```

```bash
git push origin v0.15.0
```

```bash
node scripts/release-notes.mjs 0.15.0 release-notes.md
```

```bash
gh release create v0.15.0 --title "PugIDE 0.15.0" --notes-file release-notes.md --verify-tag
```

```bash
git push origin <SHA del merge>:refs/heads/release
```

Antes del último, comprueba el fast-forward: `git merge-base --is-ancestor origin/release <SHA>`.

## Qué lleva v0.15.0

### Añadido
- **Ver diferencias antes de elegir en un conflicto** (espacios de trabajo, app de escritorio; diseño P-37, aprobado). Cuando un archivo cambia en el disco mientras aquí tiene cambios sin guardar, la barra de conflicto ofrece **«Ver diferencias»**: las dos versiones lado a lado («Aquí (sin guardar)» y «En el disco»), con lo que cambia resaltado con signo y color, el número de cambios y de líneas, y saltos al cambio anterior y siguiente (Alt+↑ / Alt+↓). Se decide ahí mismo o en la barra. **La versión que no se elige queda en «Historial del archivo»**, así que elegir mal ya no pierde trabajo. Si el archivo se borró en el disco, lo dice y ofrece conservarlo o borrarlo aquí. Escenario `66-conflictos-diferencias` y pruebas unitarias de `sideBySideDiff`.

### Cambiado
- **La zona de Datos, tan clara como la de traducciones** (diseño P-38, aprobado). Los datos se ven en una **tabla CLAVE / VALOR**, como al abrir un archivo de `locales/`: cada grupo dice cuántos elementos tiene (`{4}`, `[3]`), los valores largos ocupan una línea (enteros al editar o al pasar el ratón) y se sigue editando en el sitio: textos, números e interruptores para los sí/no; **Esc deshace lo escrito** en un campo. La cabecera queda ordenada: arriba el **juego de datos con su nombre entero** (antes se cortaba en «Por defect»), el **dado** para regenerar y «⋯»; debajo un **filtro nuevo** (busca en claves y valores, sin tildes ni mayúsculas, y abre los grupos donde hay coincidencias; Esc lo limpia) y Árbol / JSON. Una tira fina resume cuántas claves hay o cuántas coinciden y reúne deshacer, rehacer, **contraer todo** y **expandir todo**. Las claves que la plantilla no lee llevan un **punto ámbar «sin usar»** (antes ese aviso solo salía en el Registro). En el modo JSON, el mismo campo busca en el texto: cuenta las coincidencias e Intro salta de una a otra. Escenario `67-datos-tabla` y pruebas unitarias de `dataTable` y `findFolded`.
- Las notas de cada release terminan con **«Cambios completos»**: el enlace al CHANGELOG de esa versión y a todos los cambios desde la anterior en GitHub (`releaseBody` en `scripts/release-notes.mjs`, que usa `npm run release:deploy`).

### Corregido
- **«Cargar el del disco» no cargaba nada si el archivo en conflicto era el que tenías abierto** (y lo mismo al recargarse solo un archivo abierto que cambió fuera): el editor seguía con el texto antiguo y, al guardar, volvía a escribirlo en disco encima de lo que había llegado. Ahora el editor toma la versión del disco.
- **Escribir ya no da tirones en proyectos con muchas imágenes o fuentes.** Cada autoguardado (un segundo después de dejar de escribir) volvía a escribir en la biblioteca del navegador el proyecto entero, **incluidas todas las imágenes y fuentes**, con la pantalla congelada mientras tanto: medido en Chromium, unos 1,85 ms por MB (49 ms con 25 MB, 92 ms con 50 MB, 185 ms con 100 MB). Ahora la biblioteca guarda las imágenes y fuentes de cada proyecto **aparte** del texto y solo las reescribe cuando cambian (añadir, quitar o sustituir); el autoguardado escribe solo el texto y los datos (menos de 1 ms). Los proyectos guardados con versiones anteriores se siguen abriendo con sus imágenes y pasan al formato nuevo la primera vez que se guardan. Escenario `65-biblioteca-assets` (IndexedDB de verdad, también el formato anterior) y pruebas de la biblioteca.
- **Sin conexión, los iconos y las fuentes podían salir como texto.** El service worker guardaba la app pero no sus fuentes (`/media/*.woff2`, 308 KB): sin red solo aparecían si el navegador aún las tenía en su caché, y los Chromium recientes ya no las sirven así. Ahora se guardan con la app. Lo destapó el escenario `05` al subir de Chromium.
- Las pruebas de interfaz del CI volvían a fallar sin probar nada: GitHub pasó `ubuntu-latest` a Ubuntu 26.04 y Playwright 1.56.1 no sabe instalar ahí los navegadores. `playwright-core` sube a 1.65.1 (en local, tras `npm install`, vuelve a ejecutar `npx playwright-core install chromium firefox webkit`).

## Comprobar después: la primera actualización con «Actualizar»

- Cuando el flujo «Escritorio» adjunte los instaladores, la release debe llevar **`latest.yml`**, **`latest-linux.yml`**
  y los **`*.blockmap`** (como la 0.14.0). Sin ellos, «Actualizar» dice que no hay versión nueva o da error 404.
- Abre la **0.14.0 instalada con el instalador** de Windows (no el portable) o un AppImage/.deb de Linux: debe salir la
  barra «PugIDE 0.15.0 disponible». Pulsa **«Actualizar»** → progreso → **«Reiniciar y actualizar»**. Al volver a abrir,
  el aviso dice «se ha actualizado a 0.15.0» y tus proyectos y espacios siguen ahí.
- El portable de Windows y macOS siguen con **«Descargar»** (abre la release).
- Las notas de la release terminan con **«Cambios completos»** (enlace al CHANGELOG y a los cambios desde la 0.14.0).
- En la web (incógnito): la zona de **Datos** se ve como tabla CLAVE / VALOR con el filtro; y tras una visita, sin
  conexión (DevTools → Network → Offline y recargar), **los iconos se dibujan** (no salen como palabras).
