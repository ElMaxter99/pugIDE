# Publicar v0.19.0 (2026-11-19)

Guía para quien despliega (una persona o un agente). Más contexto del proceso: [docs/RELEASE.md](../RELEASE.md).

## El comando

Con el PR de la versión **mergeado en `master`** y su CI en verde, desde la carpeta del proyecto:

```bash
npm run release:deploy
```

Es el mismo en PowerShell, Bash y CI. No hay que pasarle versión ni commit: se pone en `master`, lo actualiza (si no tienes cambios sin guardar), lee la versión que declara (`0.19.0`), encuentra su commit (el merge del PR de la versión) y:

1. Comprueba que ese commit lleva la versión en `package.json` y su sección fechada del CHANGELOG.
2. Crea y sube el tag anotado `v0.19.0` (si ya existe, comprueba que apunta a ese commit; un tag publicado no se mueve).
3. Crea la release de GitHub con las notas del CHANGELOG (si ya existe, la deja).
4. Deja la rama `release` (la de producción en Vercel) en ese commit, solo si es fast-forward. Si no lo es, **no fuerza nada** y se detiene con un aviso.

Se puede repetir sin miedo: lo que ya está hecho se salta. Antes de lanzarlo de verdad se puede ver qué haría:

```bash
npm run release:deploy -- --dry-run
```

Otras opciones: `--no-prod` (tag y release de GitHub sin tocar `release`), `0.19.0` como argumento (una versión concreta, por si `master` ya declara otra) y `--sha COMMIT` / `--remote NOMBRE` (casos raros).

Necesita `git` con permiso de push de tags y de la rama `release`, y `gh` (GitHub CLI) con sesión iniciada. Los agentes de IA que preparan la versión **no** pueden empujar tags ni `release`: lo lanza una persona o el agente de despliegue con esos permisos.

## Lo único que queda a mano: Vercel

Cuando el script termina, la rama `release` ya está bien puesta. Falta desplegarla en Vercel:

- Vercel → proyecto `pug-ide` → **Deployments** → el despliegue de la rama `release` (su commit es el de la versión) → **Promote to Production** (o **Redeploy**). Si la rama de producción configurada es `release`, el push ya lo habrá lanzado: comprueba que su despliegue está en verde.

## Los instaladores de escritorio salen solos

Al publicarse la release, el flujo `Escritorio` (`.github/workflows/desktop.yml`) construye los instaladores de Windows, macOS y Linux (sin firmar), los prueba y los **adjunta a la release** de GitHub, con el aviso de «sin firmar» en sus notas. Tarda unos 15–25 minutos y no hay que hacer nada:

- Mira en GitHub → **Actions** → **Escritorio** que la web y las tres máquinas (Linux, Windows, macOS) terminan en verde, y que la release de `v0.19.0` tiene sus archivos (`.exe`, `.dmg`, `.AppImage`, `.deb`, `.rpm`).
- Si algo falla, repítelo: Actions → **Escritorio** → *Run workflow* con el tag `v0.19.0` (o `gh workflow run desktop.yml -f tag=v0.19.0`).
- Guía para quien instala: [docs/INSTALAR.md](../INSTALAR.md).

## Comprobación a mano en producción

Con una ventana de incógnito (el service worker de la PWA cachea la versión anterior):

- Carga el editor y la vista previa, y el Workspace muestra `v0.19.0`.
- `Ctrl+V` pega en el editor.
- La consola del navegador no muestra violaciones de CSP.
- Una plantilla con imágenes remotas se ve.

## Si algo falla

- **«No es fast-forward»:** `release` tiene algo que `master` no tiene. No fuerces nada: investígalo y avisa.
- **El tag ya existe y apunta a otro commit:** un tag publicado no se mueve. Investígalo.
- **`gh` falla:** inicia sesión con `gh auth login` y repite el comando (el tag no se vuelve a crear).
- **Volver atrás, rápido:** en Vercel → Deployments, el despliegue de producción anterior → **Promote to Production** (o **Instant Rollback**).
- **Volver atrás, definitivo:** corregir en `master` con un PR, publicar un parche y repetir. No se reescribe el historial ni se reutilizan tags.

## Los mismos pasos a mano (por si el script no se puede usar)

```bash
git fetch origin master release --tags
```

```bash
git tag -a v0.19.0 <SHA del merge del PR de la versión> -m "PugIDE 0.19.0"
```

```bash
git push origin v0.19.0
```

```bash
node scripts/release-notes.mjs 0.19.0 release-notes.md
```

```bash
gh release create v0.19.0 --title "PugIDE 0.19.0" --notes-file release-notes.md --verify-tag
```

```bash
git push origin <SHA del merge>:refs/heads/release
```

Antes del último, comprueba el fast-forward: `git merge-base --is-ancestor origin/release <SHA>`.

## Qué lleva v0.19.0

### Añadido
- **El traductor de la vista previa entiende más formas de i18n:** valor por defecto (`t('K', 'Texto')`, `{ defaultValue }`), lista de claves de reserva, espacios de nombres `ns:clave` (un nivel más dentro del idioma), `%{nombre}` y `{{- nombre}}`, `$t(otra.clave)`, contexto, y **plurales** (`_one`/`_other`/`_zero` con las reglas del idioma de los datos, `_plural`, ICU `{count, plural, …}` y `a | b | c` de vue-i18n). `req.t`, `res.__` y `locals.t` se detectan como traducciones.
- **Prueba de actualización de punta a punta en CI** (Linux, AppImage): construye una versión vieja y una nueva, sirve la nueva desde un GitHub falso local y comprueba con la app real que se actualiza, y que con la huella alterada se niega y no cambia nada (`desktop/test/update-e2e.mjs`).
- **macOS: descargar la actualización dentro de la app** (diseño P-48). Como la app no está firmada, macOS no deja que se actualice sola; ahora «Actualizar» descarga el `.dmg` de tu arquitectura (Intel o Apple Silicon) a Descargas con barra de progreso, **comprueba su huella SHA-512** contra la publicada en la release (si no coincide, lo borra y no abre nada) y ofrece «Abrir el instalador». Arrastra PugIDE a Aplicaciones y la primera vez ábrela con clic derecho → Abrir.
- **Versión y actualizaciones** (escritorio y web; diseño P-47 a P-49, aprobado). El **número de versión** de la barra lateral es ahora un botón que abre el panel «Versión y actualizaciones»: versión instalada (con la etiqueta «pruebas» si lo es), cómo está instalada la copia y qué pasará al actualizar (instalador de Windows: sin contraseña de administrador; AppImage: sustituye su archivo; `.deb`/`.rpm`: el sistema pide la contraseña; macOS: descarga manual del `.dmg`). En la web solo enseña la versión y el enlace a las novedades.
- **Canal de actualizaciones: Estable o Pruebas** (escritorio). «Estable» (por defecto) solo ofrece versiones publicadas; «Pruebas» ofrece también las candidatas (`-rc.N`). La versión más nueva se elige por número real (`rc.2 < rc.10 < estable`), nunca baja de versión y se recuerda entre sesiones.
- **Avisos del flujo de actualizar:** si se cierra el cuadro de la contraseña (`.deb`/`.rpm`), la descarga queda guardada y se puede reintentar; si el instalador de una versión aún se está construyendo, lo dice.
- **`npm run release:deploy -- X.Y.Z-rc.N`** publica una versión de pruebas: tag y release marcada «pre-release» en GitHub, sin mover la rama `release` (producción sigue en la última estable).

### Cambiado
- **Textos largos de ejemplo en el idioma de los datos.** `observaciones`, `descripcion`, `resumen`, `mensaje`, `nota`… salían en latín («Lorem ipsum»); ahora son frases corrientes de un documento comercial en español o en inglés según el idioma de los datos (y los títulos y palabras sueltas igual). Auditoría de fidelidad, sección de datos: 23 de 23.
- **Datos de ejemplo más creíbles para los campos de negocio.** Antes salían en latín o con un tipo raro; ahora, por el nombre del campo, salen valores con su forma y que pasan sus comprobaciones: `moneda` / `currency` (`EUR`, `USD`), `iban` (un IBAN español con los dígitos de control correctos), `nif` / `dni` / `nie` (con su letra), `cif`, `ean` / `barcode` (EAN-13 con su dígito de control), `provincia` / `province`, `razonSocial`, `peso`, `altura`, números de factura, albarán o pedido (`FA-2026-0312`, `INV-2026-0312`), `totalPages` (un entero, antes salía `25.65`), fechas de nacimiento en el pasado, y `lang` / `idioma` / `language` / `locale` con un código de idioma (`es`, `es-ES`) en lugar de texto en latín. Lo que ya funcionaba no cambia. Medido con `npm run audit:fidelidad`: la sección de datos de ejemplo pasa de 3 a 21 de 23 casos.
