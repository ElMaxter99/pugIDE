# Publicar v0.11.0 (2026-11-11)

Guía para quien despliega (una persona o un agente). Más contexto del proceso: [docs/RELEASE.md](../RELEASE.md).

## El comando

Con el PR de la versión **mergeado en `master`** y su CI en verde, desde la carpeta del proyecto:

```bash
npm run release:deploy
```

Es el mismo en PowerShell, Bash y CI. No hay que pasarle versión ni commit: se pone en `master`, lo actualiza (si no tienes cambios sin guardar), lee la versión que declara (`0.11.0`), encuentra su commit (el merge del PR de la versión) y:

1. Comprueba que ese commit lleva la versión en `package.json` y su sección fechada del CHANGELOG.
2. Crea y sube el tag anotado `v0.11.0` (si ya existe, comprueba que apunta a ese commit; un tag publicado no se mueve).
3. Crea la release de GitHub con las notas del CHANGELOG (si ya existe, la deja).
4. Deja la rama `release` (la de producción en Vercel) en ese commit, solo si es fast-forward. Si no lo es, **no fuerza nada** y se detiene con un aviso.

Se puede repetir sin miedo: lo que ya está hecho se salta. Antes de lanzarlo de verdad se puede ver qué haría:

```bash
npm run release:deploy -- --dry-run
```

Otras opciones: `--no-prod` (tag y release de GitHub sin tocar `release`), `0.11.0` como argumento (una versión concreta, por si `master` ya declara otra) y `--sha COMMIT` / `--remote NOMBRE` (casos raros).

Necesita `git` con permiso de push de tags y de la rama `release`, y `gh` (GitHub CLI) con sesión iniciada. Los agentes de IA que preparan la versión **no** pueden empujar tags ni `release`: lo lanza una persona o el agente de despliegue con esos permisos.

## Lo único que queda a mano: Vercel

Cuando el script termina, la rama `release` ya está bien puesta. Falta desplegarla en Vercel:

- Vercel → proyecto `pug-ide` → **Deployments** → el despliegue de la rama `release` (su commit es el de la versión) → **Promote to Production** (o **Redeploy**). Si la rama de producción configurada es `release`, el push ya lo habrá lanzado: comprueba que su despliegue está en verde.

## Los instaladores de escritorio salen solos

Al publicarse la release, el flujo `Escritorio` (`.github/workflows/desktop.yml`) construye los instaladores de Windows, macOS y Linux (sin firmar), los prueba y los **adjunta a la release** de GitHub, con el aviso de «sin firmar» en sus notas. Tarda unos 15–25 minutos y no hay que hacer nada:

- Mira en GitHub → **Actions** → **Escritorio** que la web y las tres máquinas (Linux, Windows, macOS) terminan en verde, y que la release de `v0.11.0` tiene sus archivos (`.exe`, `.dmg`, `.AppImage`, `.deb`, `.rpm`).
- Si algo falla, repítelo: Actions → **Escritorio** → *Run workflow* con el tag `v0.11.0` (o `gh workflow run desktop.yml -f tag=v0.11.0`).
- Guía para quien instala: [docs/INSTALAR.md](../INSTALAR.md).

## Comprobación a mano en producción

Con una ventana de incógnito (el service worker de la PWA cachea la versión anterior):

- Carga el editor y la vista previa, y el Workspace muestra `v0.11.0`.
- `Ctrl+V` pega en el editor.
- La consola del navegador no muestra violaciones de CSP.
- Una plantilla con imágenes remotas se ve.

## Si algo falla

- **«No es fast-forward»:** `release` tiene algo que `master` no tiene. No fuerces nada: investígalo y avisa.
- **El tag ya existe y apunta a otro commit:** un tag publicado no se mueve. Investígalo.
- **`gh` falla:** inicia sesión con `gh auth login` y repite el comando (el tag no se vuelve a crear).
- **Volver atrás, rápido:** en Vercel → Deployments, el despliegue de producción anterior → **Promote to Production** (o **Instant Rollback**).
- **Volver atrás, definitivo:** corregir en `master` con un PR, publicar un parche y repetir. No se reescribe el historial ni se reutilizan tags.

## Los mismos pasos a mano (por si el script no se puede usar)

```bash
git fetch origin master release --tags
```

```bash
git tag -a v0.11.0 <SHA del merge del PR de la versión> -m "PugIDE 0.11.0"
```

```bash
git push origin v0.11.0
```

```bash
node scripts/release-notes.mjs 0.11.0 release-notes.md
```

```bash
gh release create v0.11.0 --title "PugIDE 0.11.0" --notes-file release-notes.md --verify-tag
```

```bash
git push origin <SHA del merge>:refs/heads/release
```

Antes del último, comprueba el fast-forward: `git merge-base --is-ancestor origin/release <SHA>`.

## Qué lleva v0.11.0

### Añadido
- **Exportar para correo** (diseño P-23, aprobado). «Exportar → HTML para correo…» (y la paleta) pasa el CSS a atributos `style` respetando la cascada (`!important`, especificidad y orden; el `style` propio se conserva), quita `<script>` y los atributos de eventos, conserva `@media` y `:hover` en un `<style>` y permite un texto de vista previa del correo. Mide el peso contra los **102 KB a partir de los que Gmail recorta** y avisa de lo que el correo no admite: flexbox y grid (Outlook), `position`, fuentes web, imágenes sin `alt`, `<form>`, `<video>`… Con «Copiar HTML» y «Descargar .html». Sin incrustar las imágenes locales, llevan la ruta del proyecto y se avisa. Todo en el navegador.
- **Documentos de varias páginas** (P-24). En el modo PDF, **navegador de páginas**: anterior y siguiente, «ir a la página», Re Pág / Av Pág y un panel «Páginas» con una ficha por hoja, que marca las que tienen un aviso de corte. **«Exportar → Todas las plantillas (.zip)…»** compila cada plantilla que es una página (los parciales de `include` y `extends` no) a un `.html` autocontenido, sin cambiar la vista previa; las que no compilan se dicen. **Los enlaces entre plantillas** (`a(href="factura.pug")`) previsualizan esa plantilla al pulsarlos y pasan a `.html` al exportar.
- **Plantillas propias** (P-25). «Proyecto → Guardar como plantilla…» guarda el proyecto abierto (archivos y, si se quiere, datos, imágenes y fuentes e idiomas) como punto de partida. «Mis proyectos» enseña **«Mis plantillas»** con Usar, Renombrar, Actualizar con el proyecto abierto, Exportar (`.zip`) y Borrar, e «Importar plantilla (.zip)…». Hasta 30 plantillas de 25 MB, guardadas en el navegador (IndexedDB).
- Escenarios `56-exportar-correo`, `57-varias-paginas` y `58-plantillas-propias`, y pruebas unitarias de `email-export.util`, `user-template.util` y de las páginas y enlaces de `pug-vfs.util`.
- **Espacios de trabajo por cliente, en la app de escritorio** (diseño P-26, aprobado). Un espacio es **una carpeta de tu equipo** con nombre y color. «Espacios de trabajo…» (barra superior, menú «Espacios», Ctrl+Mayús+E o la paleta) lista los espacios, crea uno eligiendo la carpeta (usa lo que ya hay en ella o empieza con una plantilla) y avisa si una carpeta ya no se encuentra. Con un espacio abierto, **lo que editas se guarda en sus archivos** (los datos en `.pugide/datasets.json`), así que puedes usar git u otro editor a la vez; **lo que cambia fuera se recarga solo** y, si cambió en los dos sitios, se pregunta con cuál quedarse. La barra enseña el espacio, su carpeta y «Guardado en disco». Lo que la app no maneja (otros tipos de archivo, `.git`, `node_modules`) no se toca. La app vuelve a abrir el último espacio al arrancar. En la web y la PWA no cambia nada.
- **Aviso de versión nueva, en la app de escritorio** (P-27). **Apagado mientras no lo aceptes**: se pregunta una sola vez. Si lo permites, la app consulta en github.com (una vez al día y al abrir) el número de la última versión, sin enviar nada tuyo; con versión nueva sale una barra con **«Descargar»**, que abre la página de la versión en el navegador. No instala nada sola (los instaladores no están firmados). «Ayuda → Buscar actualizaciones…» busca a mano y cambia la preferencia.
- Seguridad de la app de escritorio: el acceso al disco pasa por una lista corta de operaciones y **solo dentro de las carpetas elegidas con el diálogo del sistema**; no se puede leer ni escribir fuera. Pruebas: la prueba real de Electron abre un espacio en una carpeta temporal, edita dentro y fuera y comprueba que no se sale de ella; pruebas unitarias de la sincronización, de la lectura y escritura de carpetas y de la comparación de versiones.

### Corregido
- La app de escritorio no reconocía sus propias direcciones internas (`pugide://`): «Abrir en una pestaña nueva» de la vista previa y los enlaces `pugide://` no funcionaban.
