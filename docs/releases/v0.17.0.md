# Publicar v0.17.0 (2026-11-17)

Guía para quien despliega (una persona o un agente). Más contexto del proceso: [docs/RELEASE.md](../RELEASE.md).

## El comando

Con el PR de la versión **mergeado en `master`** y su CI en verde, desde la carpeta del proyecto:

```bash
npm run release:deploy
```

Es el mismo en PowerShell, Bash y CI. No hay que pasarle versión ni commit: se pone en `master`, lo actualiza (si no tienes cambios sin guardar), lee la versión que declara (`0.17.0`), encuentra su commit (el merge del PR de la versión) y:

1. Comprueba que ese commit lleva la versión en `package.json` y su sección fechada del CHANGELOG.
2. Crea y sube el tag anotado `v0.17.0` (si ya existe, comprueba que apunta a ese commit; un tag publicado no se mueve).
3. Crea la release de GitHub con las notas del CHANGELOG (si ya existe, la deja).
4. Deja la rama `release` (la de producción en Vercel) en ese commit, solo si es fast-forward. Si no lo es, **no fuerza nada** y se detiene con un aviso.

Se puede repetir sin miedo: lo que ya está hecho se salta. Antes de lanzarlo de verdad se puede ver qué haría:

```bash
npm run release:deploy -- --dry-run
```

Otras opciones: `--no-prod` (tag y release de GitHub sin tocar `release`), `0.17.0` como argumento (una versión concreta, por si `master` ya declara otra) y `--sha COMMIT` / `--remote NOMBRE` (casos raros).

Necesita `git` con permiso de push de tags y de la rama `release`, y `gh` (GitHub CLI) con sesión iniciada. Los agentes de IA que preparan la versión **no** pueden empujar tags ni `release`: lo lanza una persona o el agente de despliegue con esos permisos.

## Lo único que queda a mano: Vercel

Cuando el script termina, la rama `release` ya está bien puesta. Falta desplegarla en Vercel:

- Vercel → proyecto `pug-ide` → **Deployments** → el despliegue de la rama `release` (su commit es el de la versión) → **Promote to Production** (o **Redeploy**). Si la rama de producción configurada es `release`, el push ya lo habrá lanzado: comprueba que su despliegue está en verde.

## Los instaladores de escritorio salen solos

Al publicarse la release, el flujo `Escritorio` (`.github/workflows/desktop.yml`) construye los instaladores de Windows, macOS y Linux (sin firmar), los prueba y los **adjunta a la release** de GitHub, con el aviso de «sin firmar» en sus notas. Tarda unos 15–25 minutos y no hay que hacer nada:

- Mira en GitHub → **Actions** → **Escritorio** que la web y las tres máquinas (Linux, Windows, macOS) terminan en verde, y que la release de `v0.17.0` tiene sus archivos (`.exe`, `.dmg`, `.AppImage`, `.deb`, `.rpm`).
- Si algo falla, repítelo: Actions → **Escritorio** → *Run workflow* con el tag `v0.17.0` (o `gh workflow run desktop.yml -f tag=v0.17.0`).
- Guía para quien instala: [docs/INSTALAR.md](../INSTALAR.md).

## Comprobación a mano en producción

Con una ventana de incógnito (el service worker de la PWA cachea la versión anterior):

- Carga el editor y la vista previa, y el Workspace muestra `v0.17.0`.
- `Ctrl+V` pega en el editor.
- La consola del navegador no muestra violaciones de CSP.
- Una plantilla con imágenes remotas se ve.

## Si algo falla

- **«No es fast-forward»:** `release` tiene algo que `master` no tiene. No fuerces nada: investígalo y avisa.
- **El tag ya existe y apunta a otro commit:** un tag publicado no se mueve. Investígalo.
- **`gh` falla:** inicia sesión con `gh auth login` y repite el comando (el tag no se vuelve a crear).
- **Volver atrás, rápido:** en Vercel → Deployments, el despliegue de producción anterior → **Promote to Production** (o **Instant Rollback**).
- **Volver atrás, definitivo:** corregir en `master` con un PR, publicar un parche y repetir. No se reescribe el historial ni se reutilizan tags.

## Los mismos pasos a mano (por si el script no se puede usar)

```bash
git fetch origin master release --tags
```

```bash
git tag -a v0.17.0 <SHA del merge del PR de la versión> -m "PugIDE 0.17.0"
```

```bash
git push origin v0.17.0
```

```bash
node scripts/release-notes.mjs 0.17.0 release-notes.md
```

```bash
gh release create v0.17.0 --title "PugIDE 0.17.0" --notes-file release-notes.md --verify-tag
```

```bash
git push origin <SHA del merge>:refs/heads/release
```

Antes del último, comprueba el fast-forward: `git merge-base --is-ancestor origin/release <SHA>`.

## Qué lleva v0.17.0

### Añadido
- **Varios PDF… en un solo paso** (app de escritorio; diseño P-42, aprobado). En «Exportar», justo debajo de «PDF…»: **un PDF por plantilla** (con los datos actuales; los parciales no se exportan y las plantillas que no compilan se avisan antes) o **un PDF de la misma plantilla por cada juego de datos** (`factura - Clínica Aurora.pdf`, con el idioma que se elija). Se guardan en una carpeta o en un `.zip`, con tamaño y márgenes de cada documento o uno común, y número de página opcional. Si ya hay archivos con esos nombres se pregunta una vez («Reemplazar» o «Guardar con otro nombre»), se ve «Generando presupuesto.pdf · 2 de 4», se puede cancelar a mitad y, si alguno falla, los demás se guardan y se dice cuál («Ver en Problemas»). Usa el mismo motor que «PDF…», sin red.
- **Importar datos desde una operación de OpenAPI** (web y escritorio; diseño P-43, aprobado). Hasta ahora, importar un OpenAPI creaba una clave por cada esquema del documento, que casi nunca coincide con lo que recibe la plantilla. Ahora «Importar JSON, Schema u OpenAPI…» abre un diálogo donde se **elige la operación** (`GET /facturas/{id}`) **y su respuesta** (la primera 2xx con JSON, por defecto), con filtro, vista previa de los datos y aviso de las claves que la plantilla usa y la respuesta no trae (`cliente.email`). Los valores salen de los ejemplos del documento o se generan. Las operaciones sin datos (204, PDF) salen apagadas con el motivo, **«Importar todos los esquemas»** sigue disponible y un OpenAPI sin operaciones se importa como siempre. Acepta **`.yaml` y `.yml`** además de JSON (OpenAPI 3.x y Swagger 2). No se llama a la API: solo se lee el archivo elegido. Un `$ref` a otro archivo no se sigue y se avisa.
