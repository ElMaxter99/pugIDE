# Publicar v0.14.0 (2026-11-12)

Guía para quien despliega (una persona o un agente). Más contexto del proceso: [docs/RELEASE.md](../RELEASE.md).

## El comando

Con el PR de la versión **mergeado en `master`** y su CI en verde, desde la carpeta del proyecto:

```bash
npm run release:deploy
```

Es el mismo en PowerShell, Bash y CI. No hay que pasarle versión ni commit: se pone en `master`, lo actualiza (si no tienes cambios sin guardar), lee la versión que declara (`0.14.0`), encuentra su commit (el merge del PR de la versión) y:

1. Comprueba que ese commit lleva la versión en `package.json` y su sección fechada del CHANGELOG.
2. Crea y sube el tag anotado `v0.14.0` (si ya existe, comprueba que apunta a ese commit; un tag publicado no se mueve).
3. Crea la release de GitHub con las notas del CHANGELOG (si ya existe, la deja).
4. Deja la rama `release` (la de producción en Vercel) en ese commit, solo si es fast-forward. Si no lo es, **no fuerza nada** y se detiene con un aviso.

Se puede repetir sin miedo: lo que ya está hecho se salta. Antes de lanzarlo de verdad se puede ver qué haría:

```bash
npm run release:deploy -- --dry-run
```

Otras opciones: `--no-prod` (tag y release de GitHub sin tocar `release`), `0.14.0` como argumento (una versión concreta, por si `master` ya declara otra) y `--sha COMMIT` / `--remote NOMBRE` (casos raros).

Necesita `git` con permiso de push de tags y de la rama `release`, y `gh` (GitHub CLI) con sesión iniciada. Los agentes de IA que preparan la versión **no** pueden empujar tags ni `release`: lo lanza una persona o el agente de despliegue con esos permisos.

## Lo único que queda a mano: Vercel

Cuando el script termina, la rama `release` ya está bien puesta. Falta desplegarla en Vercel:

- Vercel → proyecto `pug-ide` → **Deployments** → el despliegue de la rama `release` (su commit es el de la versión) → **Promote to Production** (o **Redeploy**). Si la rama de producción configurada es `release`, el push ya lo habrá lanzado: comprueba que su despliegue está en verde.

## Los instaladores de escritorio salen solos

Al publicarse la release, el flujo `Escritorio` (`.github/workflows/desktop.yml`) construye los instaladores de Windows, macOS y Linux (sin firmar), los prueba y los **adjunta a la release** de GitHub, con el aviso de «sin firmar» en sus notas. Tarda unos 15–25 minutos y no hay que hacer nada:

- Mira en GitHub → **Actions** → **Escritorio** que la web y las tres máquinas (Linux, Windows, macOS) terminan en verde, y que la release de `v0.14.0` tiene sus archivos (`.exe`, `.dmg`, `.AppImage`, `.deb`, `.rpm`).
- Si algo falla, repítelo: Actions → **Escritorio** → *Run workflow* con el tag `v0.14.0` (o `gh workflow run desktop.yml -f tag=v0.14.0`).
- Guía para quien instala: [docs/INSTALAR.md](../INSTALAR.md).

## Comprobación a mano en producción

Con una ventana de incógnito (el service worker de la PWA cachea la versión anterior):

- Carga el editor y la vista previa, y el Workspace muestra `v0.14.0`.
- `Ctrl+V` pega en el editor.
- La consola del navegador no muestra violaciones de CSP.
- Una plantilla con imágenes remotas se ve.

## Si algo falla

- **«No es fast-forward»:** `release` tiene algo que `master` no tiene. No fuerces nada: investígalo y avisa.
- **El tag ya existe y apunta a otro commit:** un tag publicado no se mueve. Investígalo.
- **`gh` falla:** inicia sesión con `gh auth login` y repite el comando (el tag no se vuelve a crear).
- **Volver atrás, rápido:** en Vercel → Deployments, el despliegue de producción anterior → **Promote to Production** (o **Instant Rollback**).
- **Volver atrás, definitivo:** corregir en `master` con un PR, publicar un parche y repetir. No se reescribe el historial ni se reutilizan tags.

## Los mismos pasos a mano (por si el script no se puede usar)

```bash
git fetch origin master release --tags
```

```bash
git tag -a v0.14.0 <SHA del merge del PR de la versión> -m "PugIDE 0.14.0"
```

```bash
git push origin v0.14.0
```

```bash
node scripts/release-notes.mjs 0.14.0 release-notes.md
```

```bash
gh release create v0.14.0 --title "PugIDE 0.14.0" --notes-file release-notes.md --verify-tag
```

```bash
git push origin <SHA del merge>:refs/heads/release
```

Antes del último, comprueba el fast-forward: `git merge-base --is-ancestor origin/release <SHA>`.

## Qué lleva v0.14.0

### Añadido
- **Actualizar dentro de la app de escritorio** (diseño P-35 y P-36, aprobado). La barra de versión nueva ya no ofrece «Descargar» (que abría GitHub) sino **«Actualizar»**: descarga la versión nueva de la release, con barra de progreso y «Cancelar» mientras sigues trabajando; comprueba que el archivo es el publicado (huella SHA-512) y la instala con **«Reiniciar y actualizar»** (guarda antes) o **«Al cerrar PugIDE»**. Al volver a abrir avisa de que se ha actualizado. **«Ver novedades»** abre la página de la versión en GitHub. Funciona con el instalador de Windows y en Linux (AppImage, .deb y .rpm; con .deb/.rpm el sistema pide la contraseña). En macOS (exige apps firmadas) y en el portable de Windows sigue «Descargar». Si la descarga falla o no coincide, no se instala nada y se ofrece «Reintentar» o «Descargar desde GitHub». Probado de verdad con un AppImage 0.13.9 que se actualizó a 0.14.0 desde un servidor local (y que se negó con una huella cambiada). Se usa electron-updater; cada release lleva ahora `latest*.yml` y `*.blockmap`. **La primera versión que se actualiza sola es la 0.14.0**: a ella se llega con «Descargar».
- **Guía reutilizable de cómo se actualiza una app de escritorio** ([docs/ACTUALIZAR-ESCRITORIO.md](docs/ACTUALIZAR-ESCRITORIO.md)): por qué la web es fácil y el escritorio no, los manifiestos, el código mínimo, qué sistemas se actualizan solos sin firma, seguridad, lista de comprobación y cómo probarlo con un servidor local.
- Escenario `64-actualizar-escritorio` y pruebas unitarias de `selfUpdateSupport` y del actualizador (con uno falso).
- **Comprobación de palabras prohibidas** (`scripts/check-forbidden-words.mjs`, dentro de `npm run lint` y, por tanto, del CI): falla si en cualquier archivo del repositorio aparece una palabra de la lista, sin distinguir mayúsculas ni tildes y también dentro de otras palabras. Sirve para que no se cuele el nombre de un cliente real en los ejemplos. La lista (`scripts/forbidden-words.json`) guarda solo el SHA-256 de cada palabra, nunca la palabra; se añade una con `node scripts/check-forbidden-words.mjs --hash palabra`.

### Corregido
- **`npm run build:prod` (y `npm run start:desktop`) ya no fallan en Windows con «render-sandbox.js desactualizado».** En un clon hecho antes de fijar los saltos de línea a LF (o con `core.autocrlf=true`), las fuentes del motor llegan con CRLF y su hash no coincidía con el de los archivos generados, aunque el código fuera el mismo. La comprobación ya no depende de los saltos de línea.
- **`npm run start:desktop` funciona a la primera.** Si faltaban las dependencias de la app de escritorio daba «"electron" no se reconoce como un comando»; ahora las instala sola la primera vez y cuando cambia `desktop/package-lock.json` (`scripts/ensure-desktop-deps.mjs`). Lo mismo `test:desktop` y `desktop:pack`.
- **La app de escritorio desde el código ya no dice «tienes la 0.0.0».** Con `npm run start:desktop` leía la versión de `desktop/package.json` (siempre 0.0.0, la real la pone el CI al empaquetar) y el aviso de versión nueva lo decía; ahora usa la del proyecto. Para probar el aviso: `PUGIDE_FAKE_VERSION=0.1.0 npm run start:desktop`.
- **App de escritorio: el icono de la ventana va dentro de los instaladores.** La ventana usaba `build/icon.png`, que no se empaquetaba; en Linux eso dejaba el icono de Electron. Ahora se empaquetan el PNG y un `.ico` nuevo con todos los tamaños de Windows (16 a 256 px, generado por `npm run brand:icons`), Windows agrupa la barra de tareas con el identificador de PugIDE también al ejecutar desde el código, y la prueba automática de escritorio comprueba que el icono está.

## Comprobar después: la primera versión que se actualiza sola

- Cuando el flujo «Escritorio» adjunte los instaladores, la release debe llevar también **`latest.yml`** (Windows),
  **`latest-linux.yml`** y los **`*.blockmap`**. Sin ellos, «Actualizar» de las versiones siguientes no funcionará.
- Desde la 0.13.0 instalada se llega a la 0.14.0 con **«Descargar»** (esa versión no sabe actualizarse). Instálala
  encima: se conservan proyectos, espacios y ajustes.
- A partir de aquí, en el instalador de Windows y en Linux, la próxima versión (0.14.1 o 0.15.0) se instalará con
  **«Actualizar»**. Cómo probarlo antes sin publicar: [ACTUALIZAR-ESCRITORIO.md](../ACTUALIZAR-ESCRITORIO.md), apartado 3.1.
