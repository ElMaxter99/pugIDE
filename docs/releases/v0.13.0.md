# Publicar v0.13.0 (2026-11-12)

Guía para quien despliega (una persona o un agente). Más contexto del proceso: [docs/RELEASE.md](../RELEASE.md).

## El comando

Con el PR de la versión **mergeado en `master`** y su CI en verde, desde la carpeta del proyecto:

```bash
npm run release:deploy
```

Es el mismo en PowerShell, Bash y CI. No hay que pasarle versión ni commit: se pone en `master`, lo actualiza (si no tienes cambios sin guardar), lee la versión que declara (`0.13.0`), encuentra su commit (el merge del PR de la versión) y:

1. Comprueba que ese commit lleva la versión en `package.json` y su sección fechada del CHANGELOG.
2. Crea y sube el tag anotado `v0.13.0` (si ya existe, comprueba que apunta a ese commit; un tag publicado no se mueve).
3. Crea la release de GitHub con las notas del CHANGELOG (si ya existe, la deja).
4. Deja la rama `release` (la de producción en Vercel) en ese commit, solo si es fast-forward. Si no lo es, **no fuerza nada** y se detiene con un aviso.

Se puede repetir sin miedo: lo que ya está hecho se salta. Antes de lanzarlo de verdad se puede ver qué haría:

```bash
npm run release:deploy -- --dry-run
```

Otras opciones: `--no-prod` (tag y release de GitHub sin tocar `release`), `0.13.0` como argumento (una versión concreta, por si `master` ya declara otra) y `--sha COMMIT` / `--remote NOMBRE` (casos raros).

Necesita `git` con permiso de push de tags y de la rama `release`, y `gh` (GitHub CLI) con sesión iniciada. Los agentes de IA que preparan la versión **no** pueden empujar tags ni `release`: lo lanza una persona o el agente de despliegue con esos permisos.

## Lo único que queda a mano: Vercel

Cuando el script termina, la rama `release` ya está bien puesta. Falta desplegarla en Vercel:

- Vercel → proyecto `pug-ide` → **Deployments** → el despliegue de la rama `release` (su commit es el de la versión) → **Promote to Production** (o **Redeploy**). Si la rama de producción configurada es `release`, el push ya lo habrá lanzado: comprueba que su despliegue está en verde.

## Los instaladores de escritorio salen solos

Al publicarse la release, el flujo `Escritorio` (`.github/workflows/desktop.yml`) construye los instaladores de Windows, macOS y Linux (sin firmar), los prueba y los **adjunta a la release** de GitHub, con el aviso de «sin firmar» en sus notas. Tarda unos 15–25 minutos y no hay que hacer nada:

- Mira en GitHub → **Actions** → **Escritorio** que la web y las tres máquinas (Linux, Windows, macOS) terminan en verde, y que la release de `v0.13.0` tiene sus archivos (`.exe`, `.dmg`, `.AppImage`, `.deb`, `.rpm`).
- Si algo falla, repítelo: Actions → **Escritorio** → *Run workflow* con el tag `v0.13.0` (o `gh workflow run desktop.yml -f tag=v0.13.0`).
- Guía para quien instala: [docs/INSTALAR.md](../INSTALAR.md).

## Comprobación a mano en producción

Con una ventana de incógnito (el service worker de la PWA cachea la versión anterior):

- Carga el editor y la vista previa, y el Workspace muestra `v0.13.0`.
- `Ctrl+V` pega en el editor.
- La consola del navegador no muestra violaciones de CSP.
- Una plantilla con imágenes remotas se ve.

## Si algo falla

- **«No es fast-forward»:** `release` tiene algo que `master` no tiene. No fuerces nada: investígalo y avisa.
- **El tag ya existe y apunta a otro commit:** un tag publicado no se mueve. Investígalo.
- **`gh` falla:** inicia sesión con `gh auth login` y repite el comando (el tag no se vuelve a crear).
- **Volver atrás, rápido:** en Vercel → Deployments, el despliegue de producción anterior → **Promote to Production** (o **Instant Rollback**).
- **Volver atrás, definitivo:** corregir en `master` con un PR, publicar un parche y repetir. No se reescribe el historial ni se reutilizan tags.

## Los mismos pasos a mano (por si el script no se puede usar)

```bash
git fetch origin master release --tags
```

```bash
git tag -a v0.13.0 <SHA del merge del PR de la versión> -m "PugIDE 0.13.0"
```

```bash
git push origin v0.13.0
```

```bash
node scripts/release-notes.mjs 0.13.0 release-notes.md
```

```bash
gh release create v0.13.0 --title "PugIDE 0.13.0" --notes-file release-notes.md --verify-tag
```

```bash
git push origin <SHA del merge>:refs/heads/release
```

Antes del último, comprueba el fast-forward: `git merge-base --is-ancestor origin/release <SHA>`.

## Qué lleva v0.13.0

### Añadido
- **Asistente de IA, solo en la app de escritorio y en local** (diseño P-30 a P-34, aprobado). Propone **datos de ejemplo coherentes** con la plantilla (leyendo sus `include`, `mixin` y la forma de los datos) y **arreglos de errores** desde «Problemas». Usa la CLI que ya tienes instalada, con tu sesión: **Claude Code** (`claude`) o **GitHub Copilot** (`copilot`); eliges el proveedor y el **modelo por defecto** de cada una en «Vista → Asistente de IA…». No es un botón mágico: antes de enviar ves **qué se manda** (puedes quitar archivos), la **estimación de tokens** y la orden exacta; mientras trabaja ves los pasos y los **tokens consumidos**; y las propuestas se **prueban en la vista previa**, se **revierten** o se **aplican** (con deshacer). La CLI se lanza **sin herramientas**: no puede leer ni escribir archivos ni ejecutar órdenes. En la web publicada no aparece nada. Con `npm start` hace falta abrir el puente local con `npm run ia` (solo escucha en 127.0.0.1). El Registro apunta cada petición y la barra de estado suma la sesión.
- **Guía para probar una rama en tu equipo** ([docs/PROBAR-EN-LOCAL.md](docs/PROBAR-EN-LOCAL.md)): Windows y Ubuntu, la web en local, el asistente, la app de escritorio desde el código, los instaladores de la PR o compilados por ti y cómo comprobar el aviso de versión nueva.
- Escenario `63-asistente-ia` y pruebas unitarias de `ai.util`, de las CLI (`desktop/src/ai-cli.cjs`, con CLI falsas y una respuesta real grabada) y del puente.

### Cambiado
- `npm run start:desktop` abre la app de escritorio con el código actual y `npm run test:desktop` lanza su prueba automática (los nombres antiguos `desktop:start` y `desktop:test` siguen valiendo). La guía [docs/PROBAR-EN-LOCAL.md](docs/PROBAR-EN-LOCAL.md) explica la batería completa en Windows y Ubuntu, también en Firefox y WebKit.

### Corregido
- **Una plantilla que lee un elemento por su posición ya no falla con los datos de ejemplo.** Con `productos[1].name`, PugIDE no entendía el índice: trataba `productos` como un texto y la vista previa daba «Cannot read properties of undefined (reading 'name')». Ahora reconoce `lista[N]` (también dentro de un `each`) como un elemento de la lista y se asegura de que haya al menos N+1: los datos de ejemplo nuevos se generan con esos elementos, y si tus datos ya tenían menos, se completan copiando la forma del último, sin tocar los que había. Escenario `62-indices-en-datos` y pruebas unitarias del parser y de `padArray`.
