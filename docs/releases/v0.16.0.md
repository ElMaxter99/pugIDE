# Publicar v0.16.0 (2026-11-16)

Guía para quien despliega (una persona o un agente). Más contexto del proceso: [docs/RELEASE.md](../RELEASE.md).

## El comando

Con el PR de la versión **mergeado en `master`** y su CI en verde, desde la carpeta del proyecto:

```bash
npm run release:deploy
```

Es el mismo en PowerShell, Bash y CI. No hay que pasarle versión ni commit: se pone en `master`, lo actualiza (si no tienes cambios sin guardar), lee la versión que declara (`0.16.0`), encuentra su commit (el merge del PR de la versión) y:

1. Comprueba que ese commit lleva la versión en `package.json` y su sección fechada del CHANGELOG.
2. Crea y sube el tag anotado `v0.16.0` (si ya existe, comprueba que apunta a ese commit; un tag publicado no se mueve).
3. Crea la release de GitHub con las notas del CHANGELOG (si ya existe, la deja).
4. Deja la rama `release` (la de producción en Vercel) en ese commit, solo si es fast-forward. Si no lo es, **no fuerza nada** y se detiene con un aviso.

Se puede repetir sin miedo: lo que ya está hecho se salta. Antes de lanzarlo de verdad se puede ver qué haría:

```bash
npm run release:deploy -- --dry-run
```

Otras opciones: `--no-prod` (tag y release de GitHub sin tocar `release`), `0.16.0` como argumento (una versión concreta, por si `master` ya declara otra) y `--sha COMMIT` / `--remote NOMBRE` (casos raros).

Necesita `git` con permiso de push de tags y de la rama `release`, y `gh` (GitHub CLI) con sesión iniciada. Los agentes de IA que preparan la versión **no** pueden empujar tags ni `release`: lo lanza una persona o el agente de despliegue con esos permisos.

## Lo único que queda a mano: Vercel

Cuando el script termina, la rama `release` ya está bien puesta. Falta desplegarla en Vercel:

- Vercel → proyecto `pug-ide` → **Deployments** → el despliegue de la rama `release` (su commit es el de la versión) → **Promote to Production** (o **Redeploy**). Si la rama de producción configurada es `release`, el push ya lo habrá lanzado: comprueba que su despliegue está en verde.

## Los instaladores de escritorio salen solos

Al publicarse la release, el flujo `Escritorio` (`.github/workflows/desktop.yml`) construye los instaladores de Windows, macOS y Linux (sin firmar), los prueba y los **adjunta a la release** de GitHub, con el aviso de «sin firmar» en sus notas. Tarda unos 15–25 minutos y no hay que hacer nada:

- Mira en GitHub → **Actions** → **Escritorio** que la web y las tres máquinas (Linux, Windows, macOS) terminan en verde, y que la release de `v0.16.0` tiene sus archivos (`.exe`, `.dmg`, `.AppImage`, `.deb`, `.rpm`).
- Si algo falla, repítelo: Actions → **Escritorio** → *Run workflow* con el tag `v0.16.0` (o `gh workflow run desktop.yml -f tag=v0.16.0`).
- Guía para quien instala: [docs/INSTALAR.md](../INSTALAR.md).

## Comprobación a mano en producción

Con una ventana de incógnito (el service worker de la PWA cachea la versión anterior):

- Carga el editor y la vista previa, y el Workspace muestra `v0.16.0`.
- `Ctrl+V` pega en el editor.
- La consola del navegador no muestra violaciones de CSP.
- Una plantilla con imágenes remotas se ve.

## Si algo falla

- **«No es fast-forward»:** `release` tiene algo que `master` no tiene. No fuerces nada: investígalo y avisa.
- **El tag ya existe y apunta a otro commit:** un tag publicado no se mueve. Investígalo.
- **`gh` falla:** inicia sesión con `gh auth login` y repite el comando (el tag no se vuelve a crear).
- **Volver atrás, rápido:** en Vercel → Deployments, el despliegue de producción anterior → **Promote to Production** (o **Instant Rollback**).
- **Volver atrás, definitivo:** corregir en `master` con un PR, publicar un parche y repetir. No se reescribe el historial ni se reutilizan tags.

## Los mismos pasos a mano (por si el script no se puede usar)

```bash
git fetch origin master release --tags
```

```bash
git tag -a v0.16.0 <SHA del merge del PR de la versión> -m "PugIDE 0.16.0"
```

```bash
git push origin v0.16.0
```

```bash
node scripts/release-notes.mjs 0.16.0 release-notes.md
```

```bash
gh release create v0.16.0 --title "PugIDE 0.16.0" --notes-file release-notes.md --verify-tag
```

```bash
git push origin <SHA del merge>:refs/heads/release
```

Antes del último, comprueba el fast-forward: `git merge-base --is-ancestor origin/release <SHA>`.

## Qué lleva v0.16.0

### Añadido
- **Pasar un proyecto de «Mis proyectos» a una carpeta del disco** (app de escritorio; diseño P-41, aprobado). Cada proyecto de «Mis proyectos» tiene **«Pasar a una carpeta…»**: se elige la carpeta y el nombre del espacio, y PugIDE escribe allí sus archivos, imágenes, fuentes y juegos de datos (`.pugide/datasets.json`) y la abre como espacio de trabajo. **Nunca sobrescribe nada**: si la carpeta ya tiene archivos con el mismo nombre lo dice antes y los del proyecto se guardan como «main (2).pug». Por defecto se conserva la copia en «Mis proyectos» (se puede quitar al terminar). Si no se puede escribir (sin permiso), lo dice, no cambia nada en «Mis proyectos», no deja un espacio a medias y ofrece «Elegir otra carpeta». Escenario `71-pasar-a-carpeta`, pruebas unitarias y la prueba de escritorio con Electron (la carpeta ya tenía un `main.pug`, que queda intacto).
- **Abrir archivos .pug y carpetas con PugIDE** (app de escritorio; diseño P-40, aprobado). Con la app instalada, **doble clic** en un `.pug` o `.jade` (o «Abrir con → PugIDE») lo abre en PugIDE, y se puede **arrastrar un archivo o una carpeta a la ventana**. Al abrir una plantilla suelta se pregunta si abrir **su carpeta como espacio de trabajo** (recomendado: así funcionan `include`, `extends`, estilos e imágenes; se abre con esa plantilla en la vista previa) o **solo ese archivo** en un proyecto nuevo de la app (una copia), con «Hacer siempre esto». Si la carpeta ya es un espacio, no pregunta. Con PugIDE ya abierto, el archivo llega a la misma ventana. Una carpeta soltada se abre como espacio; los archivos soltados se añaden al proyecto abierto (como «Importar archivos»). Los instaladores registran `.pug` y `.jade` **sin quitar el programa que ya tengas por defecto** (Windows y macOS: solo en «Abrir con»; Linux: `.deb` y `.rpm`). Escenario `70-abrir-con-pugide`, pruebas unitarias y la prueba de escritorio con Electron (abrir la app con un `.pug`, crear el espacio con la carpeta entera y recibir otro archivo en una segunda instancia).
- **Exportar PDF con el motor nativo** (app de escritorio; diseño P-39, aprobado). En el menú «Exportar», «Imprimir o guardar como PDF» se divide en **«PDF…»** (nuevo) e **«Imprimir…»**. «PDF…» genera el PDF directamente con el Chromium de la app, sin el diálogo de imprimir: con el tamaño y los márgenes del documento (`@page`), fondos y colores, **texto seleccionable, enlaces que funcionan y PDF etiquetado** (accesible), y se elige la plantilla, el papel (el del documento, A4, A5 o Carta), la orientación, los márgenes, el número de página abajo («3 de 12») y si abrirlo al terminar. Se guarda con el diálogo del sistema, empezando en la carpeta del espacio de trabajo (o en Descargas) y recordando la última carpeta y las opciones. Al terminar, un aviso con páginas, tamaño y carpeta, y los botones «Abrir» y «Mostrar en la carpeta». Si la plantilla no compila no se genera nada y se ofrece «Ver en Problemas»; si faltan imágenes se avisa antes. El PDF se genera en una ventana oculta sin JavaScript, sin Node y sin red. En la web no cambia nada. Escenario `69-pdf-nativo`, pruebas unitarias y la prueba de escritorio con Electron (comprueba que el archivo es un PDF con fuentes incrustadas y etiquetado).

### Cambiado
- **La vista PDF ya no se congela con tablas de miles de filas.** Paginar una tabla de 5000 filas con cabecera pasa de unos 2,5 s a unos 0,6 s, y un cambio de código con esa tabla, de 5,7 s a 1,7 s (en Firefox la mejora es mayor: de unos 9 s a 1,5 s con 1500 filas). Las posiciones de las filas se calculan en vez de volver a medir la tabla entera en cada hoja; el resultado es el mismo (idéntico en Chromium y WebKit, con diferencias de centésimas de píxel en Firefox). Medidas y método en `docs/ARCHITECTURE.md`.
- **Dependencias al día y `npm audit` a cero.** Angular 22.2.6, Monaco 0.57, `sass` 1.108.2, Electron 45.3 (app de escritorio) y **ESLint 10**, que trae `minimatch` 11 y cierra los avisos moderados que arrastrábamos (fase 13.1). Monaco 0.57 traía un DOMPurify con un aviso crítico (`<= 3.4.16`): se fuerza la 3.4.18 con `overrides`, igual que `minimatch` 11 para `typescript-eslint`. Los iconos siguen en `material-symbols` 0.48.3 porque la 0.49 quita `crop_landscape` (el botón «Horizontal» del PDF). En `desktop/` quedan avisos moderados de `minimatch` dentro de `electron-builder`, que solo se usa al empaquetar y no llega a la app.

### Corregido

- **Escritorio: en el primer arranque, la bienvenida ya no tapa «Abrir factura.pug».** Si la app se abre por primera vez con un archivo o una carpeta (doble clic o «Abrir con»), la bienvenida no se pone encima de la pregunta: queda para el siguiente arranque.
- **Los proyectos de más de unos 5 MB ya no se pierden al recargar.** La sesión (archivos, datos y pestañas) se guardaba solo en `localStorage`, que admite unos 5 MB: con datos importados grandes la barra decía «No se pudo guardar» y al recargar se volvía a la versión anterior. Ahora, si no cabe, se guarda en IndexedDB (la misma base del navegador que ya guarda los proyectos y las imágenes), sin aviso porque ya no hace falta, y al arrancar se lee de ahí. La copia anterior solo se borra cuando la nueva está escrita. El aviso sigue saliendo si no se puede guardar en ningún sitio (modo privado estricto, disco lleno), y el texto de la barra de estado, que estaba en inglés, ahora está en español. Escenario `68-sesion-grande` (localStorage lleno de verdad y recarga, en los tres navegadores).
- **`npm run release:deploy` desde una copia sin actualizar publicaba con el script antiguo.** La 0.15.0 se publicó desde una copia en la 0.13 y sus notas salieron sin «Cambios completos». Ahora el script siempre usa el de `origin/master` (si el de tu copia es otro, lo dice y ejecuta el de master) y, si una release ya creada no lleva «Cambios completos», se lo añade antes de la sección de instaladores sin tocar lo demás. Pruebas en `release-deploy.test.mjs`.
