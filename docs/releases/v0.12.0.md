# Publicar v0.12.0 (2026-11-12)

Guía para quien despliega (una persona o un agente). Más contexto del proceso: [docs/RELEASE.md](../RELEASE.md).

## El comando

Con el PR de la versión **mergeado en `master`** y su CI en verde, desde la carpeta del proyecto:

```bash
npm run release:deploy
```

Es el mismo en PowerShell, Bash y CI. No hay que pasarle versión ni commit: se pone en `master`, lo actualiza (si no tienes cambios sin guardar), lee la versión que declara (`0.12.0`), encuentra su commit (el merge del PR de la versión) y:

1. Comprueba que ese commit lleva la versión en `package.json` y su sección fechada del CHANGELOG.
2. Crea y sube el tag anotado `v0.12.0` (si ya existe, comprueba que apunta a ese commit; un tag publicado no se mueve).
3. Crea la release de GitHub con las notas del CHANGELOG (si ya existe, la deja).
4. Deja la rama `release` (la de producción en Vercel) en ese commit, solo si es fast-forward. Si no lo es, **no fuerza nada** y se detiene con un aviso.

Se puede repetir sin miedo: lo que ya está hecho se salta. Antes de lanzarlo de verdad se puede ver qué haría:

```bash
npm run release:deploy -- --dry-run
```

Otras opciones: `--no-prod` (tag y release de GitHub sin tocar `release`), `0.12.0` como argumento (una versión concreta, por si `master` ya declara otra) y `--sha COMMIT` / `--remote NOMBRE` (casos raros).

Necesita `git` con permiso de push de tags y de la rama `release`, y `gh` (GitHub CLI) con sesión iniciada. Los agentes de IA que preparan la versión **no** pueden empujar tags ni `release`: lo lanza una persona o el agente de despliegue con esos permisos.

## Lo único que queda a mano: Vercel

Cuando el script termina, la rama `release` ya está bien puesta. Falta desplegarla en Vercel:

- Vercel → proyecto `pug-ide` → **Deployments** → el despliegue de la rama `release` (su commit es el de la versión) → **Promote to Production** (o **Redeploy**). Si la rama de producción configurada es `release`, el push ya lo habrá lanzado: comprueba que su despliegue está en verde.

## Los instaladores de escritorio salen solos

Al publicarse la release, el flujo `Escritorio` (`.github/workflows/desktop.yml`) construye los instaladores de Windows, macOS y Linux (sin firmar), los prueba y los **adjunta a la release** de GitHub, con el aviso de «sin firmar» en sus notas. Tarda unos 15–25 minutos y no hay que hacer nada:

- Mira en GitHub → **Actions** → **Escritorio** que la web y las tres máquinas (Linux, Windows, macOS) terminan en verde, y que la release de `v0.12.0` tiene sus archivos (`.exe`, `.dmg`, `.AppImage`, `.deb`, `.rpm`).
- Si algo falla, repítelo: Actions → **Escritorio** → *Run workflow* con el tag `v0.12.0` (o `gh workflow run desktop.yml -f tag=v0.12.0`).
- Guía para quien instala: [docs/INSTALAR.md](../INSTALAR.md).

## Comprobación a mano en producción

Con una ventana de incógnito (el service worker de la PWA cachea la versión anterior):

- Carga el editor y la vista previa, y el Workspace muestra `v0.12.0`.
- `Ctrl+V` pega en el editor.
- La consola del navegador no muestra violaciones de CSP.
- Una plantilla con imágenes remotas se ve.

## Si algo falla

- **«No es fast-forward»:** `release` tiene algo que `master` no tiene. No fuerces nada: investígalo y avisa.
- **El tag ya existe y apunta a otro commit:** un tag publicado no se mueve. Investígalo.
- **`gh` falla:** inicia sesión con `gh auth login` y repite el comando (el tag no se vuelve a crear).
- **Volver atrás, rápido:** en Vercel → Deployments, el despliegue de producción anterior → **Promote to Production** (o **Instant Rollback**).
- **Volver atrás, definitivo:** corregir en `master` con un PR, publicar un parche y repetir. No se reescribe el historial ni se reutilizan tags.

## Los mismos pasos a mano (por si el script no se puede usar)

```bash
git fetch origin master release --tags
```

```bash
git tag -a v0.12.0 <SHA del merge del PR de la versión> -m "PugIDE 0.12.0"
```

```bash
git push origin v0.12.0
```

```bash
node scripts/release-notes.mjs 0.12.0 release-notes.md
```

```bash
gh release create v0.12.0 --title "PugIDE 0.12.0" --notes-file release-notes.md --verify-tag
```

```bash
git push origin <SHA del merge>:refs/heads/release
```

Antes del último, comprueba el fast-forward: `git merge-base --is-ancestor origin/release <SHA>`.

## Qué lleva v0.12.0

### Cambiado
- **«Importar archivos» añade al proyecto abierto** (diseño P-28, aprobado). El botón de subir del panel de archivos se llamaba «Importar proyecto» y creaba un proyecto nuevo con lo elegido, cuando lo que se espera de él es añadir archivos al que está abierto. Ahora es **«Importar archivos…»** (también en «Proyecto» y en la paleta): se eligen **archivos sueltos o una carpeta entera**, o se sueltan, y se guardan **dentro del proyecto abierto**, en la carpeta que se elija. Antes de escribir nada se ve qué es **nuevo**, qué **ya existe** y qué **no se admite**; con los que ya existen se elige entre no tocarlos (por defecto), sustituirlos (la versión anterior queda en «Historial del archivo») o conservar los dos (`tabla-2.pug`). Una carpeta se puede conservar como subcarpeta o volcar su contenido en el destino. Toda la importación se **deshace de una vez**. El menú de una carpeta ofrece «Importar archivos aquí…».
- **«Importar proyecto» pasa a «Mis proyectos»** (P-29), junto a «Nuevo proyecto»: desde una carpeta o desde un `.zip`. Crea un proyecto **nuevo** (con nombre libre si ya hay uno igual) y el que estaba abierto sigue guardado en la lista; ya no hace falta el aviso de «esto reemplaza todos los archivos». También está en «Proyecto», en la paleta y en la bienvenida.
- **Soltar sobre el árbol de archivos ya no sustituye el proyecto**: abre «Importar archivos» con el resumen, y la carpeta sobre la que se suelta es el destino. Un `.zip` pregunta si añadir su contenido al proyecto o abrirlo como proyecto nuevo.
- **Elegir una carpeta funciona en todos los navegadores** (también Firefox y Safari): se usa el selector de carpetas estándar en vez de la API que solo tenían Chrome y Edge. Se saltan `node_modules`, `.git` y los restos del sistema.
- El botón «Subir imágenes, fuentes o estilos» del panel y su entrada del menú desaparecen: «Importar archivos» acepta todos los tipos. Subir el archivo que falta desde su aviso en el árbol sigue igual.
- Escenarios `60-importar-archivos` y `61-importar-proyecto`, y pruebas unitarias de `import-files.util`.
- **Logo nuevo.** Sigue siendo un pug y un documento, pero ahora en una sola figura: el pug trae la hoja en la boca (mesa L-01 del lienzo, propuesta D, elegida entre diez). Sustituye al anterior, que eran dos mitades pegadas, en verde (fuera de la paleta de la app) y que no se distinguía en la pestaña del navegador. Cambian el icono de la pestaña, los iconos de la PWA instalada (también el enmascarable), los de Apple, Android y Windows, la imagen al compartir el enlace y el icono de la app de escritorio. En tamaños pequeños se usa una versión simplificada.
- Todos los iconos salen de un solo dibujo con `npm run brand:icons` (`scripts/brand-icons.mjs`); el SVG fuente queda también en `docs/brand/`.
